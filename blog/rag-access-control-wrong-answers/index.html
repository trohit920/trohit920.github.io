Zero leaks, two wrong answers

Rohit Thakur · 19 November 2026 · 6 min read

I built a local RAG assistant whose access control never leaked a single confidential passage. Then I asked it confidential questions as a user without clearance, and it answered two of them anyway: confidently, with citations, and wrong. Access control did exactly its job. Its job was smaller than I had assumed.

The question

When a user asks about something they are not cleared to see, what should a RAG system do? "Not leak it" is the obvious answer, and the easy one to test. The harder half is what the system says instead.

The setup

  • Corpus: 10 hand-written enterprise documents (expense policy, KYC/AML procedure, Q3 financials and so on), each labelled public, internal or confidential. Synthetic on purpose: public datasets have no clearance labels to test against.
  • Pipeline: a LangGraph agent with hybrid retrieval (dense bge-small plus BM25, fused by reciprocal rank), Qwen2.5-1.5B-Instruct for generation, and a groundedness check: an NLI model (nli-deberta-v3-small), with an embedding-similarity fallback, must find most answer sentences supported by retrieved text. Everything runs locally.
  • Evaluation: 16 gold questions, including 4 asked by an internal-clearance user whose answers are labelled confidential.

Code, corpus and gold set: agentic-rag-guardrails.

A policy, not a guardrail

I drew a line early between two kinds of protection. A guardrail is a classifier that judges content: the prompt-injection detector, the groundedness check. It can be wrong, so you measure its error rate. A policy is a rule you can state exactly, such as "an internal user never sees a confidential chunk", and it should be enforced where it cannot be argued with. Here that means before ranking: confidential chunks are filtered out of the search itself, so they never reach the prompt, and no instruction to the model can bring them back.

The 16-question run asks each question at the clearance it requires; the four under-clearance cases are a separate check. The policy held: zero leaks. So I looked at what the system said instead.

The surprise: passing the groundedness check is not the same as being right

I re-ran the four under-clearance questions and read every answer. The saved evaluation keeps only counts, so the wording below comes from my re-run on CPU; its counts match the saved run.

Both wrong answers passed the groundedness check. Each reuses a real figure from retrieved text: the travel policy really does cap hotel costs at USD 200 a night, and the information-security policy really does require security incidents to be reported within twenty-four hours. No document connects either figure to the question asked, yet the sentence-level check accepted both. (I did not record whether the NLI path or the similarity fallback let each one through.) The model, denied the right document, answered from the closest one it could see. A groundedness check asks "is this sentence supported by the context?", not "does this answer the question?", and here those came apart.

The second answer has a further problem. Its citation points to a chunk of the incident-response plan whose only deadlines are five business days and seventy-two hours. The twenty-four-hour rule came from a different retrieved document. The groundedness check compares the answer with all retrieved text, so a wrong citation passes as long as some other chunk supports the sentence.

My own harness overcounted

The evaluation script reported three confabulations, not two. It counts every non-refusal on these questions as wrong, without reading the answer. Reading them showed that the vendor question is fully answerable from an internal document: the onboarding procedure states the CISO approval rule. It was probably labelled confidential because a confidential document also covers it. The system's answer was correct, though less complete than the gold answer (it left out the security review), and the label was wrong. Evaluation sets need auditing too.

The tempting fix, and where it stops working

If the retrieved context is off-topic, the system should refuse. Retrieval similarity is the obvious signal: refuse when the best chunk is not close enough to the question.

A gate at 0.65, applied after the fact (I chose it by looking at this data; the agent never ran with it), would have refused the lodging-cap answer without refusing any answerable question: none scores below 0.68. The revenue question was already refused, so the gate changes one answer. The suspicious-activity question is a different story. Its accessible context includes topically close text about reporting deadlines, so its best question-to-chunk similarity is 0.69, level with legitimate questions. That same context supplied the wrong deadline. Any threshold that blocks it also blocks real answers.

Here, the one plausible wrong answer was exactly the one the similarity score could not separate. One case is not a rule, but it is the failure I would expect to grow on a real corpus, where topics blur. With 15 data points I would not ship any threshold anyway; this shows the shape of the problem, not a calibrated value.

One more correction to my earlier write-up: I had rejected the similarity gate entirely, because the denied questions appeared to reach 0.79. That 0.79 was the mislabelled vendor question. With the label fixed, the honest conclusion is narrower: a gate catches the obvious miss and not the subtle one.

What I would do in production

  • Enforce access once, at the data layer, and test it as an invariant. In this build the dense search filters inside the vector store and the keyword search filters in application code. Both work, but the rule now lives in two places that must stay in sync. One enforcement point, plus a "zero leaks" test in CI, is the version that survives an audit.
  • Check each citation against the sentence it supports. Grounding against the whole context let a wrong citation through. Checking the answer against the specific chunk it cites is cheap with the NLI model already in the pipeline.
  • Check relevance, not only groundedness. The next guardrail should ask whether the answer addresses the question: a question about a transaction amount should not get an answer about lodging. I have not built this yet, so treat it as the next experiment, not a result.
  • Decide what a refusal reveals. "That is in a document you cannot access" is more useful than a wrong answer, but it confirms the document exists. That is a product and security decision, not a modelling one, and it should be made explicitly.
  • Read the answers, not just the counts. One of my three "confabulations" was correct, and one wrong answer carried a wrong citation. Aggregate metrics hid the eval bug, the citation bug and the real failure mode.

Limits

  • A tiny evaluation. 16 questions, and only 3 that truly test the under-clearance case. This is a case study, not a rate.
  • Synthetic documents. Ten short, well-separated documents make retrieval easy: the chosen configuration scores 1.0 on every retrieval metric, and all six configurations tested reach hit@1 of 1.0. Real corpora will blur topics further, which makes the plausible-wrong-answer problem worse, not better.
  • One small model, re-run on CPU. The re-run reproduced the saved counts (one refusal, three answers), but exact wording can vary between runs and hardware.
